# Source-message identity (COM-116)

## Scope and tenant boundary

`commitmentos.source_message` records source identity metadata for `GMAIL` and `SLACK`. A record belongs to exactly one workspace. The provider identity is unique on `(workspace_id, provider, provider_account_id, provider_message_id)`, so duplicate delivery or retry returns the existing record, while identical provider IDs in different accounts or workspaces remain distinct.

`provider_account_id` is an opaque, stable account identifier supplied by a trusted provider connector; it is not an OAuth token or a client-selected workspace. `provider_message_id` is stored as an opaque, case-sensitive identifier. The persistence layer does not lowercase, Unicode-normalize, or trim either value. It rejects blank, padded, control-character, or overlong identifiers rather than silently changing them. The identity persistence layer does not call provider APIs or accept public writes; trusted server-side connectors must resolve the workspace from integration state. Workspace Gmail OAuth is implemented separately in [gmail-integration.md](gmail-integration.md).

New commitment links use `source_message_record_id`. Both the application service and a composite PostgreSQL foreign key require the source record to belong to the commitment's workspace. The legacy `source_message_id` column is retained only for compatibility with existing opaque references. Its composite foreign key resolves `(workspace_id, source_message_id)` to a legacy source record in that same workspace. The API no longer accepts arbitrary legacy IDs from clients.

## Timestamp and content policy

`provider_timestamp` is nullable and is set only when a trusted connector supplies an offset-aware source timestamp. It is not an ingestion, webhook-receipt, fetch, or server timestamp. If the provider timestamp is missing or cannot be interpreted without guessing, it remains `NULL`. `created_at` is generated by PostgreSQL when this identity row is recorded; for rows created by the legacy migration it represents migration-time row creation, not the original message time.

This increment stores identifiers and the optional provider timestamp only. It has no columns for message bodies, subject lines, snippets, headers, sender/recipient details, or OAuth credentials; those values are rejected by the identity schema and are not placed in the job queue or audit log by this feature. No message-body retention policy is implied. A later feature must receive an explicit decision on encryption, access, retention, and deletion before persisting message content.

## Legacy migration

Migration `0011_source_message_identity.sql` is additive. For every distinct non-null `(workspace_id, source_message_id)` already present on a commitment, it creates a source record whose `legacy_reference` is the exact existing string. Provider, account, provider-message ID, and provider timestamp remain `NULL`; the old commitment value is not rewritten and no event timestamp is synthesized. Composite uniqueness and foreign keys prevent a legacy reference or source record from being associated across workspaces. Source records are restricted from deletion while referenced.

## Idempotent persistence behavior

`recordSourceMessage` validates a trusted provider identity and relies on a PostgreSQL unique constraint for concurrent deduplication. A retry returns the same row and ID. If the first delivery had no provider timestamp, a later delivery may fill that unknown value from the provider. A known timestamp is never overwritten; two different known timestamps for the same identity produce a conflict instead of silently changing provenance. No raw message content is accepted by this service.

The PostgreSQL integration suite checks concurrent duplicate delivery, retry behavior, timestamp conflicts, workspace isolation, database-enforced association integrity, and migration of legacy references. It runs against the real PostgreSQL service in CI; this sandbox does not include Docker or a local PostgreSQL server.
