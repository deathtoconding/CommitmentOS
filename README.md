# CommitmentOS

CommitmentOS turns business conversations into tracked commitments so teams can follow through on what they promised.

This repository is being built in dependency-ordered increments. The current implementation establishes the application runtime, quality gates, PostgreSQL foundation, verified email/password authentication with password recovery, workspace membership management, reusable workspace authorization guards, an authenticated responsive application shell, the commitment persistence/lifecycle/workspace API, immutable commitment and workspace-administration audit history, a workspace-scoped commitment inbox and data-backed dashboard, commitment detail with a read-only audit timeline, the PostgreSQL outbox plus Redis/BullMQ worker foundation, and tenant-scoped source-message identity metadata. Provider integrations, message ingestion and extraction, and their automated product workflows remain later stages.

## Stack

- Node.js 22 and npm
- Next.js App Router, React, and TypeScript
- Better Auth with Zod input validation
- PostgreSQL with Drizzle ORM and Drizzle Kit migrations
- Redis and BullMQ for asynchronous jobs; PostgreSQL remains the durable job source of truth
- Vitest, ESLint, and Prettier

## Prerequisites

- Node.js 22 (see `.nvmrc`)
- npm 10 or later
- Docker Compose and Docker, for the included local PostgreSQL and Redis services

## Local development

```bash
npm ci
cp .env.example .env
docker compose up -d postgres redis
npm run db:migrate
npm run db:check
npm run dev
# In a second terminal, after .env is configured:
npm run worker
```

The landing page can start without PostgreSQL, but registration, sign-in, sessions, and the protected `/app` route require a reachable PostgreSQL instance. Before using the app outside local development, replace `BETTER_AUTH_SECRET` with a unique secret generated by `openssl rand -base64 32` and set `BETTER_AUTH_URL` to the canonical HTTPS origin.

Open <http://localhost:3000> after the development server starts. Configure a reachable authenticated SMTP service in `.env` before creating accounts; sign-up now requires clicking a verification link before sign-in can establish a session. Use `/signup` to create an account and `/login` to sign in. Authenticated clients can create/list workspaces, list workspace members, perform owner-only membership administration, and use workspace-scoped commitment list/create/read/update endpoints; see [workspace behavior](docs/workspaces.md) and [commitment behavior](docs/commitments.md) for routes and authorization rules.

## Quality checks

```bash
npm run format:check
npm run lint
npm run typecheck
npm test
npm run build
npm run test:integration
npm run test:jobs-integration
npm run test:source-messages-integration
npm audit --audit-level=moderate
```

`npm run test:integration` requires the database migrations to have been applied and a production build to exist. Use a dedicated local/CI test database: the script creates and removes temporary fixtures. It starts a local TLS-enabled SMTP fixture and Next.js server, follows real Better Auth verification and password-reset links, checks verification expiry and concurrent/replayed token rejection, confirms non-enumerating recovery responses and shared PostgreSQL rate limits, proves that unverified users cannot sign in or join a workspace, and checks authentication/logout, workspace authorization, commitment persistence and API behavior, tenant isolation, immutable audit records, atomic mutation/audit writes, and lifecycle transitions against PostgreSQL. `npm run test:jobs-integration` requires the same migrated test PostgreSQL plus a reachable real Redis service; it verifies durable outbox recovery, BullMQ execution, idempotency, correlation, retries/backoff, timeouts, dead-letter handling, and worker readiness. `npm run test:source-messages-integration` requires a migrated PostgreSQL test database and verifies identity deduplication, retries, tenant-scoped commitment links, and the additive legacy-reference migration. None of the integration suites silently skips when its dependencies are unavailable.

## Database migrations

Add application tables under `src/db/schema/`, then generate and review a migration:

```bash
npm run db:generate -- --name=describe-change
npm run db:migrate
```

The `commitmentos` PostgreSQL schema is reserved for application tables. Do not place credentials in source control; `.env.example` contains local-only values.

## Authentication scope

COM-104 uses Better Auth's email/password and database-session support. Passwords use Better Auth's built-in scrypt hashing; session cookies are HttpOnly and SameSite by default and Secure in production. Sign-up does not automatically establish a session, and duplicate-account registration receives a generic response to reduce account enumeration. New accounts must verify their email before a session can be created; authenticated clients cannot mark their own addresses verified. Verification and password-reset messages are delivered over authenticated SMTP with STARTTLS required except on implicit-TLS port 465. Configure `SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`, `SMTP_PASSWORD`, and `EMAIL_FROM`; use `SMTP_TLS_CA` only for a private CA bundle. Email verification links expire after 24 hours and are single-use; the database stores only a SHA-256 replay marker. Password-reset links expire after one hour, are single-use, and revoke existing sessions when consumed. Recovery responses do not reveal whether an address exists, and Better Auth rate limits are stored in PostgreSQL for shared enforcement. Use `/forgot-password` to request a recovery link. OAuth providers remain tracked follow-up work. COM-105 adds workspace membership, COM-106 adds reusable session/membership/role guards, COM-107 adds owner-only administration for existing registered accounts, COM-108 adds commitment persistence, and COM-109 adds the commitment lifecycle transition service. Email invitations and pending invites remain out of scope. COM-110 adds the workspace-scoped commitment API, COM-111 adds immutable audit history for consequential commitment mutations, and COM-112 adds the authenticated app shell with server-validated workspace selection. COM-115 adds durable asynchronous job processing; COM-116 models tenant-scoped source-message identity without storing message bodies. See [ADR-0002](docs/adr/0002-authentication.md) for the authentication decision, [authentication behavior](docs/authentication.md), [workspace behavior](docs/workspaces.md) for tenant scoping and shell behavior, [commitment behavior](docs/commitments.md) for the current aggregate and lifecycle scope, and [source-message behavior](docs/source-messages.md) for identity and retention boundaries.
